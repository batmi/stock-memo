# 주식 매매 일지 (Stock Trading Journal) - Multi-User Edition

[![License](https://img.shields.io/badge/License-Apache_2.0-blue.svg)](https://opensource.org/licenses/Apache-2.0)

개인 투자자를 위한 **로컬 기반 주식 매매 일지 및 포트폴리오 관리 웹 애플리케이션**입니다.
파이썬(Flask) 백엔드와 SQLite를 기반으로 하며, **다중 사용자(Multi-User) 환경**과 **모바일 기기 최적화**가 적용되어 언제 어디서든 안전하고 쾌적하게 매매 기록을 관리할 수 있습니다.

## 1. 프로그램 개요 및 목적 (Overview & Objective)

이 프로그램은 개인 투자자가 엑셀이나 수기 노트 대신 **웹 브라우저를 통해 직관적이고 체계적으로 매매 일지를 작성하고 포트폴리오를 관리**할 수 있도록 돕는 도구입니다.
단순한 기록을 넘어, **매매 성과 분석(승률, 손익비 등), 캘린더 뷰, 실시간 현재가 및 뉴스 연동** 기능을 제공하여 투자 복기와 전략 수립을 극대화하는 데 목적이 있습니다.

## 2. 주요 기능 상세 (Key Features)

*   **다중 사용자 & 보안 (Multi-User & Security)**
    *   회원가입 및 로그인 기능을 제공하며, 최초 가입자가 자동으로 최고 관리자로 지정되어 이후 가입자에 대한 승인 제어가 가능합니다.
    *   로그인 5회 실패 시 1분간 계정 차단, 1시간 장기간 미활동 시 5분 전 경고 및 자동 로그아웃 처리.
    *   대용량 파일 업로드 방어(16MB 제한) 및 XSS, CSRF 보안 조치 등 안전한 금융 데이터 보호가 적용되어 있습니다.
*   **매매 일지 & 스마트 에디터 (Journal & Smart Editor)**
    *   매수, 매도, 관망, 배당 기록뿐 아니라 종목에 대한 일반 메모와 아이디어를 기록할 수 있습니다.
    *   에디터 본문 내에 이미지 직접 삽입(스크린샷 클립보드 붙여넣기, 드래그 앤 드롭 지원) 및 크기 조절이 가능하며, 외부 텍스트 붙여넣기 시 색상/배경 서식을 자동 정제합니다.
*   **포트폴리오 대시보드 & 현재가 연동 (Dashboard & Real-time Price)**
    *   현재 보유 종목, 총 투자 금액, 평균 단가, 누적 실현 손익을 자동 계산하고 시각적인 파이 차트로 제공합니다. (사용자 지정 드래그 앤 드롭 정렬 지원)
    *   1분 주기 현재가 자동 업데이트를 지원하며, 정규장(KRX) 뿐만 아니라 **시간외 단일가(NXT)** 캐싱 및 토글 기능을 완벽하게 지원합니다.
    *   청산 종목 보기, 현재가 보기 등의 옵션 상태가 사용자별 설정(Preferences)에 동기화됩니다.
*   **5중 독립 필터링 (Advanced Filtering)**
    *   기록별, 종목별, 계좌별, 증권사별, 투자 분류별 5개의 독립된 필터를 통해 방대한 매매 기록을 신속하고 정밀하게 필터링하여 분석할 수 있습니다.
*   **매매 성과 분석 & 차트 뷰 (Performance Analytics)**
    *   승률, 손익비(Profit Factor), 평균 수익/손실, 최대 낙폭(MDD), 평균 보유기간 등 회고를 위한 심도 있는 통계 지표를 제공합니다.
    *   월간/주간 단위 실현 손익, 평가 손익, 매매 금액, 누적 수익금 흐름을 보여주는 인터랙티브 막대 차트를 지원하며, 차트 막대 클릭 시 해당하는 세부 거래 내역을 바로 확인할 수 있습니다.
*   **데이터 무결성 검증 (Data Integrity)**
    *   보유 수량을 초과하는 매도나 미보유 종목에 대한 매도 등, 논리적으로 잘못된 데이터 입력을 서버 단계에서 원천 차단하여 평균 단가와 실현 손익의 무결성을 유지합니다.
*   **캘린더 뷰 & 엑셀 내보내기 (Calendar & Export)**
    *   월별 달력에서 일자별 매매/메모 현황과 실현 손익을 색상 테마별로 직관적으로 파악할 수 있으며, 전체 기록을 버튼 한 번에 엑셀(XLSX) 데이터로 내보낼 수 있습니다.
*   **실시간 뉴스 연동 (Live News Integration)**
    *   보유 중이거나 최근 기록한 종목과 관련된 최신 뉴스를 구글 뉴스(RSS) 기반으로 5분 주기로 로드하여 사이드바에 제공합니다.
*   **관리자 대시보드 & 시스템 로깅 (Admin & Logging)**
    *   전체 사용자 목록, 가입/최근 접속 시간, 데이터 통계를 한눈에 확인하고 사용자 상태를 관리할 수 있는 관리자 전용 대시보드를 지원합니다.
    *   접속, 작업, 에러 로그가 매일 날짜별 파일(`logs/backend_app_*.log`)로 자동 순환 기록되며 유지보수가 간편합니다.
*   **모바일 최적화 (PWA Ready)**
    *   데스크톱/모바일 UI 자동 반응형 대응, 다크/라이트 테마 지원, iOS/Android 기기에서 홈 화면 추가 시 네이티브 앱처럼 동작하는 쾌적한 UX를 제공합니다.

## 4. 설치 및 실행 가이드 (Installation & Execution)

### 서버 실행
프로젝트 폴더로 이동한 뒤, 아래 제공되는 스크립트를 통해 로컬 서버를 실행합니다.
필수 패키지가 없으면 설치 여부를 묻고 `requirements.txt` 의 버전 범위대로 설치합니다.

**Mac / Linux 환경**
최초 1회 실행 권한을 부여한 뒤, 쉘 스크립트 형태로 간편하게 실행할 수 있습니다.
```bash
chmod +x run.sh
./run.sh
```
*(기존 방식인 `python backend_app.py` 명령어로도 동일하게 실행 가능합니다.)*

**Windows 환경**
```bash
python backend_app.py
```

포트를 바꾸려면 인자로 넘깁니다: `./run.sh 8080`

### 접속
웹 브라우저를 열고 다음 주소로 접속합니다.
```text
http://127.0.0.1:5000
```

## 5. 데이터 백업 및 보안 가이드 (Backup & Security)

### 데이터 백업 및 복구
*   **웹에서 간편하게 백업 (권장)**: 앱 화면 상단의 **[완벽 백업]** 버튼을 클릭하면 로그인한 계정의 전체 DB(`journal.db`)와 첨부 이미지가 포함된 무결성 검증 ZIP 파일이 다운로드됩니다. 새로운 환경에서 **[백업 원복]** 버튼을 통해 업로드하면 기존 상태 그대로 복원됩니다.
*   **자동 백업**: 매일 자정, 서버 내부(`backup/` 폴더)에 사용자별 백업 압축 파일이 자동 생성되며 100% 복원 가능한 상태인지 자체 무결성 검사(CRC, 레코드 수)를 수행합니다.
*   **수동 백업**: 직접 서버를 이전할 경우, 프로젝트 내의 `db/` 폴더와 `uploads/` 폴더만 복사하시면 됩니다.

### 보안 가이드 (Security Guide)
본 애플리케이션은 개인의 민감한 금융 및 투자 데이터를 다루므로 각별한 주의가 필요합니다.
*   **최고 관리자 계정**: 앱을 최초로 설치한 후 가장 처음으로 가입하는 계정이 자동으로 최고 관리자로 지정되며, 이후 가입하는 사용자는 이 관리자의 승인이 있어야 로그인이 가능합니다.
*   **세션 보안**: 내부적으로 세션 탈취(XSS) 및 크로스 사이트 요청 위조(CSRF) 방지 보안 쿠키 설정이 적용되어 있으며, 공용 기기에서의 데이터 유출을 막기 위해 1시간 동안 활동이 없으면 자동으로 로그아웃됩니다.
*   **외부 접속 주의**: 공유기 포트포워딩을 통한 직접적인 외부망(HTTP) 노출은 권장하지 않습니다. 외부(스마트폰 등)에서 안전하게 접속하려면 `ngrok`, `Cloudflare Tunnels`, `Tailscale`과 같은 암호화된 보안 터널링 서비스를 이용하시기 바랍니다.
*   **운영 환경(HTTPS)**: 로컬망에서는 `waitress`를 통해 안정적으로 구동되지만, 본격적으로 웹에 퍼블리싱 하시려면 Nginx 등의 리버스 프록시(Reverse Proxy)를 연동하여 HTTPS(SSL) 인증서를 적용하는 것을 적극 권장합니다. HTTPS 로 서비스할 때는 환경변수 `SESSION_COOKIE_SECURE=1` 을 주어 세션 쿠키가 평문 경로로 나가지 않게 하세요.
*   **정적 파일 노출 범위**: 웹으로 서빙되는 것은 `static/` 폴더와 본인 소유의 `uploads/<계정>/` 뿐입니다. DB·백업·로그·소스·`.secret_key` 는 로그인한 사용자라도 URL 로 접근할 수 없습니다. (예전에는 프로젝트 루트 전체가 열려 있었습니다 — [설계 규칙](#6-프로젝트-구조-project-structure) 참고)
*   **응답 헤더**: 모든 응답에 CSP(Content-Security-Policy), `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy` 가 붙습니다. HTTPS 요청에는 HSTS 도 함께 적용됩니다. 새 CDN 을 쓰려면 `app/routes/middleware.py` 의 CSP 목록에 출처를 추가해야 합니다 — 추가하지 않으면 브라우저가 조용히 차단합니다.
*   **무차별 대입 방어**: IP 단위 요청 제한과 계정 단위 로그인 잠금이 함께 걸려 있습니다(`app/utils/ratelimit.py` 가 슬라이딩 윈도우·실패 잠금 두 원시 타입을 단독으로 소유하고, 로그인·가입·재설정·봇 API 가 모두 그것을 씁니다). 상태가 프로세스 메모리에 있으므로 **단일 프로세스로 구동**해야 의도한 한도가 지켜집니다.

### 로그인 복구 (Password Recovery)
웹의 관리자 초기화 기능은 **관리자가 이미 로그인해 있을 때만** 쓸 수 있어, 정작 관리자 본인이 잠기면 소용이 없습니다. 이때는 서버에 접속해 복구 도구를 실행하세요. 앱이 떠 있지 않아도, 계정이 잠겨 있어도 동작하며, 변경 사항은 서버 재시작 없이 즉시 반영됩니다.

```bash
cd ~/GitHub/stock-memo
./.venv/bin/python tools/reset_password.py --list              # 계정 목록·상태 확인
./.venv/bin/python tools/reset_password.py --user <계정>        # 새 비밀번호 직접 입력
./.venv/bin/python tools/reset_password.py --user <계정> --random   # 무작위 임시 비밀번호 발급
./.venv/bin/python tools/reset_password.py --user <계정> --unlock   # 미승인/차단 상태까지 해제
```

비밀번호는 입력 시 화면에 표시되지 않고 셸 히스토리에도 남지 않습니다. 초기화 사실만 `logs/backend_app.log` 에 기록되며 비밀번호 자체는 로그에 남지 않습니다. 참고로 로그인 실패 시 서버 로그에는 실패 사유(존재하지 않는 계정 / 비밀번호 불일치)와 조회한 DB 경로가 함께 남으므로, 원인 파악은 먼저 로그를 확인하는 편이 빠릅니다.

## 6. 프로젝트 구조 (Project Structure)

```text
stock-memo/
├── backend_app.py      # 앱 조립 — 모듈 연결, 스키마 초기화, 기동(bootstrap)
├── wsgi.py             # gunicorn/uwsgi 진입점 (bootstrap 을 호출한다)
├── config.py           # 경로·상수·시크릿 키 (설정의 단일 소스 — 모든 계층이 참조)
│
├── app/                # 애플리케이션 코드 — 성격별로 묶는다
│   │
│   │  ── routes: 요청 처리 계층 (Flask 블루프린트) ──────────────
│   ├── routes/
│   │   ├── auth.py         # 로그인·가입·로그아웃·비밀번호 재설정 요청 + 세션 검사
│   │   ├── admin.py        # 관리자 — 계정 승인·삭제·비밀번호 초기화
│   │   ├── api.py          # 화면 API — 기록 CRUD, 통계, 시세, 뉴스, 봇 조작
│   │   ├── backup_api.py   # 전체 백업 ZIP 내보내기·복원
│   │   └── middleware.py   # 보안/캐시 헤더, CSP, gzip 압축, 전역 예외 처리
│   │
│   │  ── services: 도메인 계층 (Flask 비의존, 단위 테스트 용이) ──
│   ├── services/
│   │   ├── accounts.py     # 계좌번호 정규화 규칙 + 계좌 매핑 저장소
│   │   ├── stats.py        # 매매 성과 분석(통계) 계산 로직 (순수 함수)
│   │   ├── prices.py       # 현재가(시세) 조회 서비스 (provider별 분해 + 폴백)
│   │   ├── news.py         # 종목 뉴스 조회 (구글 뉴스 RSS + 캐시)
│   │   ├── backups.py      # 백업 ZIP 무결성 검증 로직 (순수 함수)
│   │   ├── images.py       # 본문 내장 base64 이미지 추출·첨부 저장
│   │   ├── users.py        # 사용자명 규칙, 비밀번호 정책, 세션 epoch, 폴더 경로
```

### 설계 규칙 (Design Rules)

이 구조를 유지하려면 아래 일곱 가지를 지켜야 합니다. 각각은 실제로 사고가 났던 지점입니다.

**1. 정적 파일은 `static/` 안에서만 서빙한다.**
예전에는 `static_folder='.'` 로 프로젝트 루트 전체가 정적 경로에 열려 있어, 로그인만
한 일반 사용자도 `/.secret_key`·`/db/journal.db`·`/backup/*.zip`·`/json/<타인>/…` 를
그대로 내려받을 수 있었습니다. 시크릿 키가 새면 세션 쿠키를 위조해 관리자를 사칭할 수
있으므로, 이는 정보 유출이 아니라 **권한 상승 경로**였습니다.
(`tests/test_middleware.py` 의 `test_sensitive_files_are_not_served` 가 회귀를 막습니다)

**2. DB 스키마는 `app/database/schema.py` 만 정의한다.**
새 컬럼은 `ADDED_COLUMNS` 에 한 줄 추가하고 `CREATE TABLE` 문에도 함께 적습니다.
앞의 것은 기존 DB 를, 뒤의 것은 새 DB 를 위한 것이라 **둘 다** 필요합니다.
`tests/test_schema.py` 가 "새로 만든 DB" 와 "옛 DB 를 마이그레이션한 DB" 가 같은 모양인지
검사합니다.

**3. 경로는 항상 `config.<이름>` 으로, 쓰는 순간에 읽는다.**
`from config import UPLOAD_FOLDER` 처럼 이름만 떼어 오면 테스트가 경로를 바꿔치기해도
복사본은 그대로라, **테스트가 통과하는데 실제로는 아무것도 검증하지 않는** 상태가 됩니다.

**4. `import backend_app` 에는 부작용이 없어야 한다.**
스키마 적용·데이터 이관·백그라운드 스레드는 `bootstrap()` 을 명시적으로 부를 때만
일어납니다. 임포트만으로 실행되면 테스트나 CLI 도구가 운영 DB 를 건드리게 됩니다.
(`tests/test_startup.py` 가 이를 검사합니다)

**5. DB 를 여는 테스트는 반드시 `app` 픽스처를 받는다.**
`app` 픽스처가 `config` 의 모든 데이터 경로를 임시 폴더로 돌립니다. 이를 받지 않고
`bootstrap()` 이나 `db_conn()` 을 부르면 **운영 DB 에 스키마 마이그레이션이 돕니다.**
`tests/conftest.py` 가 `sqlite3.connect` 를 감싸 운영 DB 경로를 여는 순간 실패시킵니다.
(파일이 바뀌었는지만 보면 부족합니다 — 스키마가 이미 최신이면 열고도 아무것도 바꾸지
않아 검사를 통과하고, 다음번에 진짜로 마이그레이션이 돕니다)

**6. 사람이 매년 채워 넣어야 하는 목록은 두지 않는다.**
KRX 휴장일이 그랬습니다. 처음엔 소스에 박힌 집합, 다음엔 `data/krx_holidays.json` —
둘 다 **연초마다 손으로 채워야 한다**는 점에서 같은 물건이었습니다. 설날·추석은
음력 환산이 필요하고 대체공휴일 규칙도 매년 따져야 하니 실제로는 미뤄지다 잊히고,
잊히면 **조용히 틀립니다** — 공휴일을 정규장으로 판정해 쉬는 날 내내 외부 API 를
두드리고 화면은 '장중'으로 표시됩니다.

지금은 [`holidays`](https://pypi.org/project/holidays/) 패키지가 계산합니다.
음력 환산과 대체공휴일 규칙이 라이브러리 몫이고, `app/services/prices.py` 는 **거래소 고유
휴장일 2건**만 얹습니다 — 근로자의 날(5/1)과 연말 폐장일(12/31)은 국가 공휴일이
아니지만 KRX 는 쉽니다. (같은 규약을 `my-stock-hts` 의 `api/market_calendar.py`
가 씁니다)

임시공휴일은 패키지가 새 버전을 내야 반영되므로 `tools/update_holidays.sh` 를
**주 1회 cron** 으로 돌립니다. 기동 경로에서 자동 업그레이드하지 않는 이유는,
휴장 판정 라이브러리가 매 기동 조용히 바뀌면 장 운영시간 판단이 사람 모르게
달라지기 때문입니다. 새 달력은 다음 재시작부터 적용됩니다.

재시작할 때마다 기동 로그가 어느 달력으로 판정하는지 못박습니다:

```
📅 휴장일 판정: holidays 0.103 (2026년 23건, 앞으로 6일 남음)
```

패키지가 없거나 계산에 실패하면 `ERROR` 로 올라오고, 화면 콘솔에도 남습니다.

**7. 모듈이 남기는 로그는 `applog.MODULE_LOGGERS` 에 등록해야 파일에 남는다.**
등록하지 않은 로거는 핸들러가 없어 루트로 전파되는데, 루트에도 핸들러가 없어
파이썬의 `lastResort` 가 WARNING 이상만 포맷 없이 stderr 로 흘리고 INFO 는
사라집니다. 실제로 모듈 분리 직후 `auth`·`admin`·`jobs`·`ratelimit`·`api`·
`backup_api` 의 로그가 전부 이 상태였습니다 — 로그인 실패 사유와 IP, 계정 잠금,
자동 백업 성패처럼 사후에 되짚어야 하는 기록이 대상이었습니다.
(`tests/test_applog.py` 가 소스를 훑어 강제합니다)

### 프런트엔드 스크립트 로드 순서

`static/js/` 의 조각들은 **ES 모듈이 아니라 순서대로 로드되는 클래식 스크립트**입니다.
최상위 `let`/`const`/`function` 이 전역 렉시컬 환경을 공유하므로, 한 덩어리였던 예전
`script.js` 와 실행 의미가 같습니다. (HTML 의 인라인 `onclick` 핸들러가 전역 함수를
직접 부르고 있어 모듈로 바꾸면 그것들이 전부 깨집니다)

*   로드 순서는 **파일명 번호 순서**이며, `backend_app.app_scripts()` 가 폴더를 읽어
    자동으로 목록을 만듭니다. 템플릿에 `<script>` 를 손으로 나열하지 않습니다.
*   ⚠️ **로드 시점에** 다른 조각의 함수를 참조하면 안 됩니다. 함수 호이스팅은 파일
    단위이므로, 뒤 파일의 함수를 앞 파일의 최상위 코드에서 참조하면 `ReferenceError`
    입니다. 이벤트 핸들러로 넘길 때는 `() => fn()` 으로 감싸 호출 시점에 찾게 합니다.

> 성과 지표(승률·손익비·월별 집계)의 정본은 백엔드 `app/services/stats.py` **하나**입니다.
> 예전에는 `static/calc.js` 에도 같은 알고리즘의 사본이 있었지만 앱에서 호출되지
> 않았으므로(분석 화면은 처음부터 `/api/stats` 를 씁니다) 삭제했습니다.
> `static/calc.js` 에는 화면이 보유 상태(평단·원가)를 굴리는 상태전이 함수만 남습니다.
> 계산식의 회귀는 `tests/test_stats.py` 가 골든 스냅샷
> (`tests/fixtures/stats_expected.json`)으로 고정합니다.

### 운영 형태 (Deployment Shape)

**이 앱은 단일 프로세스 구동을 전제로 합니다.** 통계 캐시·요청 제한·계정 잠금·시세
캐시가 모두 프로세스 메모리에 있어서, 멀티 워커(`gunicorn -w 2` 이상)로 띄우면
요청 제한이 워커 수만큼 느슨해지고 캐시가 워커마다 어긋납니다.

*   기본 실행(`python backend_app.py`)은 waitress 를 16스레드 단일 프로세스로 띄웁니다.
*   WSGI 서버를 직접 쓴다면 `wsgi:application` 을 가리키고 워커는 1개로 둡니다.
*   부득이 멀티 워커라면 워커 하나만 백그라운드 작업을 돌리도록 나머지에
    `START_BACKGROUND_JOBS=0` 을 주고, 자동 백업은 cron 으로 따로 돌립니다.

> 프로세스 메모리에만 있는 상태의 목록은 `memcache.PROCESS_LOCAL_STATE` 가 갖고
> 있으며, 서버가 뜰 때마다 기동 로그에 그대로 찍힙니다. 멀티 워커로 띄웠을 때의
> 증상(요청 제한이 헐거워지고, 저장했는데 통계가 안 바뀌고, 비밀번호를 바꿨는데
> 다른 창이 안 끊기는)은 서로 무관해 보여서 원인을 한참 뒤에야 찾게 되기 때문입니다.

## 7. 시스템 트레이딩 연동 API (Trading API)

외부 트레이딩 봇(HTS)이 체결 내역을 이 서버에 실시간으로 기록할 수 있는 REST API를 제공합니다.
전체 계약은 [`UniversalTradingHistoryAPI.json`](UniversalTradingHistoryAPI.json) (OpenAPI 3.1)에 정의되어 있습니다.

### 인증

1. 웹 대시보드 → 설정 → **HTS 연동 API 키**에서 키를 발급받습니다. (`skm_`로 시작)
2. 키를 `X-API-KEY` 헤더에 담아 `POST /api/v1/auth/token` 을 호출해 24시간 유효한 Access Token으로 교환합니다.
3. 이후 모든 요청에 `Authorization: Bearer <token>` 을 붙입니다.

> ⚠️ **키 원문은 발급 직후 한 번만 표시됩니다.** 서버에는 SHA-256 해시만 저장되어 다시 조회할 수 없습니다. 키를 폐기하면 그 키로 발급된 토큰도 즉시 무효화됩니다.

키에는 스코프가 부여되고 토큰이 이를 상속합니다 — `trades:write`(기록 생성·수정·삭제), `trades:read`(조회·동기화 지점), `bot:write`(봇 Ping).

### 주요 엔드포인트

| 메서드 | 경로 | 설명 |
|---|---|---|
| `GET` | `/api/v1/health` | 서버 상태 확인 (무인증) |
| `POST` | `/api/v1/auth/token` | API 키 → Access Token 교환 |
| `POST` | `/api/v1/trades` | 매매 기록 단건 전송 |
| `POST` | `/api/v1/trades/batch` | 일괄 전송 (최대 500건, 항목별 결과 반환) |
| `GET` | `/api/v1/trades` | 기록 조회 (대사용, 커서 페이지네이션) |
| `GET` | `/api/v1/trades/last-sync` | 마지막 동기화 지점 (백필 구간 계산) |
| `GET` | `/api/v1/trades/by-exec-id/{id}` | 멱등키로 저장 여부 확인 |
| `PATCH` / `DELETE` | `/api/v1/trades/{id}` | 기록 정정 / 삭제 |
| `POST` | `/api/v1/positions/opening` | 연동 시작 시점의 기초 보유 잔고 등록 |
| `POST` | `/api/v1/bot/status` | 봇 가동 상태 Ping |

### 설계 원칙

*   **멱등성**: `brokerExecutionId`에 UNIQUE 제약이 걸려 중복 재전송은 기존 기록을 `200`으로 돌려줍니다. 봇은 응답을 못 받으면 **무조건 재전송해도 안전**합니다. 권장 키는 `{env}:{계좌}:{체결일}:{주문번호}` — 증권사 주문번호는 영업일마다 재사용되므로 단독 사용은 금지합니다.
*   **유실 금지**: 보유 수량 초과 매도 같은 무결성 위반도 **저장하고 `needsReview`로 표시**합니다. `400`으로 되돌리면 봇이 재시도해도 계속 실패해 그 체결이 영구히 사라집니다. (웹 UI 수동 입력은 즉시 고칠 수 있으므로 종전대로 차단합니다.)
*   **모의/실거래 분리**: `isSimulated`로 분리 저장하며 기본 조회·통계에서 제외됩니다.
*   **시스템/수동 분리**: `isSystem`으로 자동매매 주문만 `시스템`으로 분류합니다. 봇은 자기 계좌의 체결을 **전부** 보고하므로(사람이 앱에서 낸 주문 포함) 이 구분이 없으면 자동매매 성과와 수동 매매가 뭉쳐집니다.
*   **거래일 귀속**: `executedAt`(오프셋 포함 RFC3339) + `exchange`로 **거래소 현지 거래일**을 산출합니다. 미국 애프터마켓 체결이 한국 날짜로 밀리지 않습니다.
*   **레이트 리밋**: 토큰 발급 IP당 5분 10회, 일반 API 키당 1분 600회. 초과 시 `429` + `Retry-After`.

### 매매 분류

`isSystem=true`면 `시스템`으로 확정하고, `false`이거나 필드가 없으면 **같은 종목의 직전 분류를 상속**하되 없으면 빈 값으로 둡니다. 봇이 `tradeClass`를 직접 지정하면 그 값을 씁니다. 기초잔고(`positions/opening`)도 `isSystem=false`입니다.

**`시스템`은 상속하지 않습니다** — 예전 버전이 봇 기록을 전부 `시스템`으로 저장해 뒀기 때문에, 상속하면 고치려던 오염이 영구화됩니다. 상속은 사람이 뜻을 담아 고른 분류(`장기투자` 등)에만 걸립니다.

> 이미 `시스템`으로 저장된 과거 기록은 멱등 처리 때문에 재동기화로도 덮이지 않습니다. 웹에서 직접 고쳐야 합니다.

### 여러 대의 봇 (botId)

하트비트와 명령의 스코프는 **API 키가 아니라 사용자**입니다(키는 인증 직후 username으로 바뀝니다). 그래서 키를 따로 발급해도 인스턴스는 갈라지지 않으며, 구분자는 Ping 본문의 `botId`입니다.

*   **상태**: 웹 표시등의 대표 상태는 **가장 나쁜 봇**을 따릅니다 — '하나라도 살아 있으면 초록'으로 하면 실전봇의 죽음이 모의봇 Ping에 가려집니다.
*   **명령**: 재동기화는 대상 봇을 지정해 큐에 넣습니다. 봇이 둘 이상인데 대상을 비우면 `400`으로 거절합니다 — 아무 봇이나 채간 뒤 ack까지 보내 화면엔 '완료'로 뜨는 **조용한 실패**가 되기 때문입니다.
*   **유령 행 정리**: 기기를 폐기하면 옛 행이 남고, 표시등이 가장 나쁜 봇을 따르므로 그 행 하나가 상태를 영구히 '통신단절'로 굳혀 **진짜 장애 신호를 죽입니다.** 목록의 `✕`로 지우세요(매매 기록은 지워지지 않고, 가동 중이면 다음 Ping에 재등록됩니다).

### 재동기화 — 지운 기록 되살리기

웹에서 기록을 지워도 봇이 자동으로 다시 보내지 않습니다(봇은 '보냈다'는 사실만 기억합니다). 이게 맞는 동작입니다 — 의도적으로 지운 기록이 되살아나면 지울 방법이 없어집니다.

**설정 → 계정 설정 → 재동기화**에서 분기(90일)/반기(180일)/1년(365일) 중 고르면 봇이 그 기간을 다시 보냅니다(모두 달력이 아닌 **롤링** 기준). 멱등 처리로 중복은 `duplicate`로 건너뛰므로 `inserted=10, skipped=80` 같은 결과가 곧 **무엇이 얼마나 지워져 있었는지에 대한 답**입니다. 중복이 공짜이니 기간은 넉넉히 잡으세요. API(`POST /api/me/bot/resync`)는 `from`/`to` 직접 지정도 받습니다.

**명령 전달**: 봇은 대개 가정용 네트워크 뒤에 있어 서버가 먼저 접속할 수 없습니다. 버튼을 누르면 `bot_commands`에 쌓이고 봇의 다음 Ping(최대 10초) 응답에 실립니다.

*   **at-most-once** — ack를 못 받아도 재전달하지 않습니다. 반복 전달하면 봇이 ack 직전에 재시작할 때 같은 재동기화가 한 번 더 돌아, 그 사이 일부러 지운 기록이 되살아납니다. 전달이 유실됐을 때 버튼을 다시 누르는 편이 낫습니다.
*   '완료'로 표시된 명령은 어떤 경우에도 다시 나가지 않습니다(봇의 중복 방지는 메모리뿐이라 이 보장은 서버가 집니다).
*   봇이 가져가지 않으면 1시간 뒤 만료되어 '미처리'로 표시됩니다. `status=stopped`인 봇에는 주지 않습니다.
*   ack 형식이 잘못돼도 Ping은 `200`으로 처리합니다 — `400`을 주면 하트비트가 끊겨 화면이 '통신단절'로 바뀝니다.

**백업 복원 뒤에는 반드시 재동기화가 필요합니다.** 백업 ZIP에는 `api_keys`·`users`가 담기지 않으므로 새 서버라면 API 키를 재발급해 봇의 `JOURNAL_API_KEY`를 교체해야 하고, 백업 이후 봇이 보낸 기록은 봇 큐에 전송 완료로 남아 백필도 잡지 못합니다. 재동기화는 봇의 로컬 거래기록을 원본으로 삼아 큐에서 이미 정리된 오래된 기록까지 복구합니다.

> ⚠️ **`pause`/`resume`은 의도적으로 구현하지 않았습니다.** 스펙 enum에는 있지만 `SUPPORTED_BOT_COMMANDS`에서 제외되어 큐 적재부터 거부합니다. 재동기화는 "이미 봇의 것인 데이터를 다시 보내라"지만 `pause`는 **웹서버가 매매봇을 정지시키는 권한**이라, 웹이 침해되면 포지션을 든 채 봇이 멈춥니다.

### 오류 응답 및 운영

```json
{ "error": "사람이 읽는 메시지", "errorCode": "OVERSELL", "details": {} }
```

분기는 반드시 `errorCode`로 하세요. `error` 문구는 예고 없이 바뀔 수 있습니다.

*   API 키가 평문으로 전송되지 않도록 **반드시 HTTPS**로 서비스하세요 (Nginx 등 리버스 프록시 + SSL).
*   레이트 리밋은 프로세스 내 메모리 기준입니다. 다중 프로세스로 확장하려면 Redis 등 공유 저장소로 교체해야 합니다.

## 8. 테스트 가이드 (Testing)

백엔드 API와 데이터 무결성 검증, 백업 복원(라운드트립), 성과 분석 로직은 `pytest` 기반 단위 테스트로 검증됩니다.
테스트 코드는 `tests/` 폴더에 위치하며, 임시 DB를 사용하므로 실제 구동 데이터(`db/journal.db`)에 영향을 주지 않습니다.

```bash
# 개발·테스트 의존성 설치 (최초 1회)
pip install -r requirements-dev.txt
playwright install chromium      # 브라우저 E2E 테스트용

# 전체 테스트 실행
pytest

# 브라우저 E2E 를 뺀 빠른 실행 (5초 내외)
pytest --ignore=tests/test_frontend.py
```

프론트엔드 보유 상태 엔진(`static/calc.js`)은 Node 내장 테스트 러너로 검증합니다.
백엔드 성과 지표는 `tests/test_stats.py` 가 골든 스냅샷으로 고정합니다.

```bash
# 프론트엔드 계산 단위 테스트 (Node 18+)
node --test tests/calc.test.js

# 백엔드 성과 지표 회귀
pytest tests/test_stats.py
```

### 린트 (Lint)

```bash
pip install ruff
ruff check .
```

규칙은 `pyproject.toml` 에 있습니다. 처음부터 넓게 켜면 기존 코드가 수백 건 걸려
아무도 안 보게 되므로, **실제 버그로 이어지는 것**(미사용/미정의 이름, 문법 오류,
흔한 함정)부터 켜 두었습니다.

### 구조를 지키는 테스트

일반적인 기능 테스트 외에, 위 "설계 규칙"이 무너지지 않도록 지키는 테스트가 있습니다.
리팩터링 중에 조용히 되돌아가기 쉬운 것들입니다.

| 파일 | 지키는 것 |
|---|---|
| `test_middleware.py::test_sensitive_files_are_not_served` | `.secret_key`·DB·백업이 정적 경로로 새지 않는다 |
| `test_middleware.py::test_every_app_script_is_listed_and_served` | `static/js` 조각이 하나도 빠지지 않고 순서대로 실린다 |
| `test_schema.py::test_migrated_legacy_db_matches_fresh_db` | 새 DB 와 마이그레이션된 옛 DB 의 스키마가 같다 |
| `test_admin.py::test_every_admin_route_is_permission_checked` | 모든 관리자 라우트가 비관리자에게 403 |
| `test_startup.py::test_importing_backend_app_has_no_side_effects` | 임포트만으로 DB·스레드가 생기지 않는다 |
| `test_accounts.py::test_trading_api_shares_the_same_rule` | 봇 API 와 웹 화면이 같은 계좌 정규화 규칙을 쓴다 |
| `test_frontend.py::test_broker_dropdown_is_built_from_the_single_source` | 증권사 목록이 한 곳에서만 정의된다 |
