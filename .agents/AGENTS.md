# Project Rules

## 1. 커밋 메시지 스타일 (Commit Message Style)
- 작업 완료 후 커밋 메시지를 작성할 때 기존의 규칙을 항상 따른다.
- **머릿말 (Conventional Commits)**: `feat(ui):`, `fix(api):`, `style(history):` 등 변경 성격과 도메인을 명시한다.
- **문체**: `~한다`, `~이다` 형태의 간결한 평어체(현재형)로 작성한다.
- **내용 (Body)**: 단순히 '무엇을 바꿨다'가 아니라, '어떤 문제가 있었고(또는 왜 바꿨고) 어떻게 동작하게 했는지'를 구체적인 맥락과 스토리로 작성한다.

### 사용자 선호 (2026-10-24)
- 커밋 메시지를 요청하면 먼저 최근 `git log`의 제목·본문 형식을 확인한다.
- 기본 범위는 마지막 커밋(HEAD) 이후의 전체 변경이다. staged·unstaged 변경과 새 파일을 모두 확인하고, 최근 요청 한 건으로 범위를 축소하지 않는다. 사용자가 범위를 따로 지정하면 그 지시를 따른다.
- Conventional Commits 제목과 한국어 현재형(`~한다`)을 사용한다. 문제와 변경 이유를 설명하는 도입 문단, 기능별 상세 변경 목록, 검증 결과 순으로 작성한다.
- 최종 코드 상태를 기준으로 정리한다. 이미 이전 커밋에 포함된 내용이나 중간에 취소한 구현을 새 변경으로 쓰지 않는다. 실제로 수행한 테스트와 확인 결과만 기재한다.
- 바로 복사할 수 있는 하나의 코드 블록으로 통합 메시지를 제안한다. Git 커밋은 사용자가 직접 수행한다.

## 2. 임시 파일 관리 (Temporary Files)
- 테스트를 위해 생성한 임시 스크립트, 데이터 파일, 또는 백그라운드 패키지(`node_modules`, `package.json` 등)는 **테스트가 끝난 직후 항상 즉시 삭제**하여 워크스페이스(git 상태)를 깔끔하게 유지한다.

## 3. 커밋 제한 (No Automatic Commits)
- 절대 Git 커밋을 자동으로 진행하지 않는다.
- 커밋은 항상 사용자가 수동으로 진행하므로, 작업 완료 후에는 **커밋 메시지만 작성해서 제안**한다.
